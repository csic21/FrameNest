# 0030 — 双语首句的有界并行与测量边界

日期：2026-10-14。任务 FN-70。基线 main `a41a21784e75eb9cd6c6646c0ad2026ed55344a4`。

## 决策

仅将当前窗口的翻译模型准备与 ASR 重叠，不增加识别窗口并发，不更换模型或线程数。
PCM 非空且通过现有静音判断后才启动准备；原文缓存命中则直接启动准备。
ML Kit 准备在 IO dispatcher 上调用既有 `ensureModel`，包括创建 Translator 和
`downloadModelIfNeeded` 的等待。SDK 不暴露其内部下载/校验/加载的分项时间，不能
将这个数值称为纯模型加载速度。实际 `translate` 仍在原文发布之后执行。

`supervisorScope` 保留翻译准备失败时的原文，所有协程从属于当前窗口；静音/空 PCM
不创建翻译客户端。识别后无文字则取消已开始的准备。ML Kit 的原生 Task 可能不能
即时停止，既有客户端所有权会拒绝晚到结果，不能声称底层下载被瞬间中止。

原文模式以相同源/目标语言绕过准备，沿用现有缓存与 MT 重试复用原文。
不删除任何权重完整性校验。退出释放、后台暂停、seek generation 与缓存 lease 不变。

## 计时解释

增加独立 `translationPreparationMs`，与 ASR 时间可能重叠；完整窗口预算继续使用
真实 wall-clock 总时长，而不是阶段之和。冷下载仍进入总预算，可能让预取暂时停止，
没有通过排除慢步骤制造好看的 RTF。现有最近窗口诊断不等于冷启动到真实屏幕显示。

首句跟踪记录初始 ASR 准备、首次非空 PCM 到达、首次原文/双语缓存就绪，以及
首次原文/双语选入当前叠层；另保留首个新生成双语窗口的阶段/提交快照，区别于
可能更早的暖缓存就绪。PCM 事件按采集时的单调时钟记时，UI 回调延迟不算作读取。
新增计时只保留本会话内存聚合；UI 可用表示当前字幕已选入
显示状态，除非有明确渲染事件，不能将其描述为屏幕呈现时刻。

## 收益与代价

确定消除“完成 ASR 后才开始翻译准备”的依赖。模型已经就绪时收益可能很小。
冷模型下载/加载可能与 ASR 争 CPU、内存或网络，必须用同设备和素材做 A/B，不能
只由并行结构推导手机一定更快。已安装模型与未下载模型分别测量。

3 秒媒体窗口不是固定等待现实时间 3 秒：NAS 文件可以超前读取；当前仍是离线整窗
识别，并未接入逐字流式模型。

## 未改变的风险/后续测量

- 相邻 PCM 缓存 miss 仍同步读额外 6 秒，可能占主要延迟；需实测后再动读取预算。
- 初始 SenseVoice 安装与 native load 各做完整校验，仍有两次约 239MB 的文件校验。
- native ASR decode 无可靠即时取消；generation 防旧结果，不等于取消耗时为零。
- 原文或译文生成时若 cue 已过期，就可能只入缓存而未显示；指标必须区分可用与可见。
- ASR 线程保持 2；旧代码的 RK3588 RTF 注释不能当 OPPO 性能证据，已纠正注释。
