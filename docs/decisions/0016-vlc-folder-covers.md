# 决策：列表封面用共享 libVLC 直连取一帧

- 状态：accepted（实现与自动测试；真机以重新进入文件夹后封面是否出现为准）
- 日期：2026-10-01
- 任务：FN-53

## 问题

0015 的本地片头在 PME110 上只盖住了文件夹里的一部分视频。有的行已经出现封面和时长，多部 2160p 仍是占位图标，还有几行一直转圈。每一张都先顺序读了一大段片头，比其他播放器的几秒慢。

## 证据

- 同一文件夹里，前缀路径至少为一份几十 GB 的文件写出了封面和时长。本地取帧本身可以成功。
- 多部 2160p 停在占位。`MediaMetadataRetriever` 拿到截断的片头后仍然没有可用帧。
- 转圈对应每个文件先复制最多 64 MB，再在单并发队列里等待。播放同一批文件走的是 libVLC 直接 SMB，不经过这段复制。
- 决策 0003 已把「单个共享 libVLC 取帧」留作 MediaMetadataRetriever 在目标 NAS 上失败时的下一步，并禁止一行一个播放器。

## 决定

1. 列表封面先用每个缩略图 worker 复用的一个 libVLC。地址与播放相同，用 `Uri` 打开不含账号的 `smb://`，不能把这段字符串当成本地文件路径。用户名、密码和域只作为媒体选项，用完即从字符数组清掉，不写入日志。
2. 不挂窗口，也不写快照文件。libVLC 3 没有缩略图接口；取帧用 `libvlc_video_set_format_callbacks` 加 `libvlc_video_set_callbacks`，把一帧 `RV32` 写进调用方的缓冲。长边 320，短边跟着片子的比例，不再把竖屏压成 16:9。格子里用完整放入，不裁切、不拉伸。解码只用 avcodec。播放仍按 0007 第 3 点走硬件解码。
3. 定位方式和播放的 SMB 一致：打开后做一次 fast seek，不用 `:start-time` 重开输入。先 8 秒，这一帧仍是黑场或纯色再试 20 秒。单个文件最多 8 秒，出了可用帧立刻停止。
4. 列表不再退回 0015 的本地前缀。16 MB 片头在真机上没有给仍是占位的文件出帧，而且每次失败都要先把这段下完。前缀代码和它的测试留着，文件夹列表不调用。
5. 默认同时取 3 张。每个 worker 自己一个播放器，彼此不再串行。设置里可以改回 1 或 2。不为每一行建播放器。
6. 封面还在生成时，格子里保持电影图标，画面到位后短淡入。缓存键不变。文件名从 `c2` 改为 `c3`，因为已经写入的 `c2` 是被压成 16:9 的。旧的 `<digest>.jpg` 仍可先显示。SMB 拖动预览见 0017。代理 AFD 仍声明 `UNKNOWN_LENGTH`。

## 未选择的方案

- 继续只靠 64 MB 片头：真机上又慢，又漏掉多部 2160p。
- 给列表挂一个播放窗口，再用 ImageReader 或快照读像素：libVLC 3 的快照依赖真实视频输出，维护者也不把远程地址交给 Android 的 ThumbnailUtils。这一版曾这样写过，文件夹里没有出封面，同一天改成内存回调。
- 升级到 libVLC 4 的 thumbnail request：3.6.5 里没有这组符号。播放内核仍是 3.x。
- 一行一个播放器：决策 0003 禁止。
- 为了跳过片头去读 30–120 秒：那一跳又会变回长时间取帧。
- 把整段播放改成软件解码：0007 第 3 点不变。软件解码只服务这一张封面的内存缓冲。
- 把 8 秒预算写成实测出图耗时：还没有在这台手机上量到新路径的单张时间。

## 后果

- 决策 0015 的本地前缀不再参与文件夹列表。它既不是主路径，也不是失败后的回退。
- 决策 0003 的默认单并发由本决策改为默认 3 路。仍不为每一行建播放器。
- 决策 0014 的长度选择继续只服务拖动预览。
- 不把以前观察到的 FUSE 失败间隔写成这条路径的出图耗时。
