# 决策：列表封面只读片头前缀

- 状态：accepted（文件夹列表已不再走这条路径。[0016](0016-vlc-folder-covers.md) 用共享 libVLC 的内存回调取一帧，失败后也不再读本地前缀。前缀实现和测试还在）
- 日期：2026-10-01
- 任务：FN-53

## 问题

0014 把已知文件大小交给了 `MediaMetadataRetriever`，手机上封面仍然转圈后回到占位图。

## 证据

PME110 上第二次打开文件夹时，取帧器日志里的 `appliedLength` 已经等于文件大小，描述符长度仍是 -1。这些文件大约从 4 GB 到 80 GB 以上。每次打开后约 6.5 秒出现 `FUSE ENOBUFS`，接着四次 `getFrameAtTime` 都是空帧，间隔只有零点几秒。没有嵌入封面。播放用的直接 SMB 路径没有参与这次取帧。

代理回调只有一条线程。内核继续排队读请求时，回复写不进去，解析停在半截，所以后面的取帧立刻为空，而不是再去读目标时间。

## 决定

1. 列表封面不再打开代理文件描述符。未走出直接播放器封面时，每个文件只通过 SMB 顺序读取最多 16 MB 片头，写到临时文件，再用本地路径取一帧。临时文件在取完后删除。最初实现是 64 MB，真机上这个上限又慢又盖不住 2160p，主路径见 0016。
2. Matroska/WebM 片头里的 Segment 长度改成未知，避免截断的前缀仍被当成几十 GB。其它封装不改字节。
3. 时长达到 1 分钟、或时长未知时，只试 2 秒、5 秒、8 秒、12 秒。更短的片子仍用 0013 的候选。黑场和纯色继续跳过。嵌入封面仍然优先。
4. 不为一行创建播放器。拖动预览仍走 0014 的代理长度，这次不改。

## 未选择的方案

- 继续把完整大小交给代理上的取帧器：真机已经这样失败。
- 为了跳过片头再去读 30–120 秒：高码率原盘上这个时间点远在 64 MB 之外，会把「先看到画面」变回长时间下载。
- 改用共享 libVLC 取帧：0003 把它留作 MMR 仍然失败时的下一步。这一步先确认本地前缀能不能出图。

## 后果

- 决策 0003 的「列表用代理 FD 取帧」由本决策替代。默认单并发、缓存键和「不为每一行建播放器」不变。
- 决策 0013 的 30–120 秒第一候选不再用于这些长视频的封面。高码率文件的封面可能仍是片头画面。
- 决策 0014 的长度选择继续只服务拖动预览。
- 不把这次观察到的失败间隔写成新路径的出图耗时。
