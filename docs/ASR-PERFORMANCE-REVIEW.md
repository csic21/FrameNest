## 已确认的处理链路

开启 → SMB 与模型准备 → 读取当前 3 秒窗口及前后各 750ms 上下文 → PCM 缓存缺失时额外解码后续 6 秒 → SenseVoice 离线识别 → 原文落盘与发布 → ML Kit 翻译 → 译文落盘 → 下一个窗口。

已有优化包括：复用 SMB 文件句柄和模型、PCM 预读、原文先发布、12/30 秒自适应预取、成功后不再固定空等 500ms、后台/seek 取消代次。它们已经存在，不能作为新优化成果。

3 秒是媒体窗口大小，不表示一定要等待现实时间 3 秒。NAS 视频可提前读取；实际瓶颈需要分开测量读取、解码、ASR 和翻译。

## 优先处理的问题

### 字幕可能生成了却完全没显示

`ListenTranslateSession.refreshActiveCue()` 始终按最新播放位置查字幕，`ListenTranslateWindows.cueAt()` 不返回已结束的 cue。例：字幕属于 0–3 秒，结果在播放到 3.5 秒后发布，它会进入缓存，但当前画面不会再显示。实际 cue 还可能短于 3 秒，因此总处理速度快于实时也不保证每句可见。

代码：`feature/listen_translate/ListenTranslateSession.kt:291`、`ListenTranslateWindows.kt:36`。

建议优先增加明确的“准备字幕后播放”路径，建立从当前播放点起的连续覆盖。普通播放不自动暂停；准备模式允许取消，seek 后重建准备目标。不要把旧字幕强行延迟显示在新画面上。

### 仅原文仍承担翻译成本

`setDisplayMode()` 只改变格式；源/目标语言不同时，实际引擎仍准备翻译模型、调用 MT，并等待结束后才跑下一窗口。原文回调已提前发生，但首轮准备和后续吞吐依然受 MT 影响。翻译失败后，重试还会重新执行音频/ASR，而非仅重试翻译。

代码：`ListenTranslateSession.kt:130,421,453`、`RealListenTranslateEngine.kt:80,159,163`、`feature/player/PlayerViewModel.kt:519`。

建议把原文完成和译文完成分别跟踪。“仅原文”无需准备/执行 MT；切到双语后复用源文补翻译；MT 失败只重试 MT。当前缓存完成条件把翻译算在内，不能只加一个跳过 `translate()` 的分支，否则会反复识别或错误标记覆盖。

### 首句被额外音频预读挡住

PCM 缓存 miss 时，`CachingListenAudioSource` 同步解码到请求终点加 6 秒才返回。片头首窗实际读取 0–9.75 秒；中段通常读取 10.5 秒媒体音频，ASR 只需要其中 4.5 秒。这里说的是媒体时长，不是等待时长。

代码：`RealListenTranslateEngine.kt:84`、`audio/ListenAudioSource.kt:196,209`。`player/audio/PcmWindowDecoder.kt` 在每次真正解码时新建 extractor/codec 并 seek；目前只复用 SMB 句柄和 PCM 缓存。

建议区分“当前急需”与“已有字幕领先量”两种读取预算：首次开启/seek 先交付必要 PCM，稳定后再增大预读。直接永久关闭 6 秒预读会增加 extractor/codec 重建，可能损害整体吞吐。持续解码器复用属于第二阶段，必须在 PCM 阶段确实占主导后实施。

### 子词拼接和末词时长影响可读性

Sherpa 适配器对每个 token `trim()`，随后业务层统一 `joinToString(" ")`。现有测试中的 `the / tri / bal / boy` 会成为 `the tri bal boy`；中文 `开 / 饭 / 时 / 间` 会成为 `开 饭 时 间`。模型返回的完整 `recognition.text` 在有时间戳时被舍弃。断词会污染交给 MT 的文本；具体翻译损失尚未做语料测量。

另一个边界是最后一个 token 的结束时间等于开始时间；只有一个 token 时，cue 可为零时长，在非精确命中的播放 tick 上看不到。

代码：`asr/SherpaAsrEngine.kt:145`、`RealListenTranslateEngine.kt:131,147`；复现输入见 `SherpaAsrMappingTest`。

建议按真实 tokenizer 的词边界规则保留/还原完整词，覆盖中文、英文子词和混合文本；裁切窗口时不能把上下文全文无条件贴回来。为没有可靠结束时间的末词设定受窗口约束的显示时长。先加端到端文本与 cue 断言，再改组句；保持媒体时间轴及 seek 隔离。

### 暂停不能积累后续字幕

预取策略在 `!playing` 时返回 0。暂停会补当前窗口，但不会继续生成未来字幕。因此“用户先暂停十秒再看”在现状下不是有效的持续缓冲方案。

代码：`ListenPrefetchPolicy.kt:26,60`。

建议把用户显式进入的“准备字幕”与普通暂停区分开。准备模式前台处理一个有界范围；普通暂停、后台、网络缓冲和离开页面保留既有节制行为。此举改变决策 0023 的播放策略，需要实现时补充决策与手机/平板验收。

### 开启阶段仍有可以测量的固定成本

准备先调用 `SherpaModelInstaller.ensureInstalled()` 验证完整模型，随后 `SherpaAsrEngine.ensureModel()` 再验证一次同一个约 239MB 权重文件；缓存字幕读取又在模型准备完成之后启动。重复打开开关会卸载/重新加载 recognizer。

代码：`asr/SherpaModelInstaller.kt:57,122`、`asr/SherpaAsrEngine.kt:49`、`feature/player/PlayerViewModel.kt:355,494,517,572`。

建议先测完整冷启动；评估在同一次、受模型所有权保护的准备过程中复用校验结果，以及先显示身份已核验的缓存字幕、按缺口惰性加载模型。不能删除完整性校验，也不能永久保留大模型来掩盖成本。

## 产品上的补偿方式

| 顺序 | 方案 | 收益与限制 |
| --- | --- | --- |
| 首选 | 增加“准备字幕后播放”入口 | 以从当前位置起连续覆盖 6–12 秒媒体时间作为待验证起点，不按固定等待秒数假装就绪；可随时继续播放或取消。 |
| 首选 | 有可靠原字幕时，优先提供字幕翻译 | 跳过 ASR，直接利用已有文本和时间轴；先支持已能读取的外挂文本字幕。内嵌字幕文本提取和图片字幕不是免费能力。 |
| 随后 | 慢设备提供明确的“先生成再观看”模式 | 长时间平均处理速度慢于播放时，短预缓冲终究会耗尽。允许用户为选定片段/整片预生成，并展示进度、取消和资源约束；不默认扫描整个 NAS。 |
| 配套 | 字幕暂缺时说明状态与恢复动作 | 区分正在准备、追赶中、未识别出文字和失败；提供准备后继续或回看上一句。不要用“预取目标 30 秒”冒充“已就绪 30 秒”。 |

领先缓冲只能吸收波动。假设处理 1 秒媒体持续需要 1.2 秒墙钟时间，在 1x 播放下只有约 0.833 秒媒体/秒的生成能力；12 秒连续缓冲约在 72 秒后耗尽。此为示例计算，不是本机测量结果。

译文质量也需要独立评价。ML Kit 官方明确将端侧翻译定位于较简单的日常翻译，非英语语言之间会经过英语中转，可能损害质量。因此日语/韩语译中文的观感差，不能全部归因于 ASR。来源：[ML Kit Translation limitations](https://developers.google.com/ml-kit/language/translation)。

## 实施与测量顺序

1. 先修 token 拼接/末词时长，并真正分离原文与翻译完成状态，避免无效 MT 和重复 ASR。
2. 加当前窗口优先的读取预算，对照现有 6 秒预读测冷首句、seek 后首句和持续吞吐；之后才决定是否复用解码器或增加有界阶段并行。
3. 实现可选准备模式、连续覆盖计算与状态提示；明确普通暂停不等于准备，准备完成也不覆盖用户手动暂停意图。
4. 同一片源对比 CPU 线程 1/2/4 的冷/热窗口、持续 15 分钟播放掉帧和热表现。当前是 CPU/int8/2 线程；没有证据支持直接加线程、换大模型或承诺倍数加速。
5. 前四项仍达不到目标时，再评估流式模型或独立的高质量转写方案。当前 `OfflineRecognizer` 每窗整段解码，不具备已接入的真实增量字幕；更换模型需单独验证准确率、Android ABI、许可、体积和生命周期。

测量至少包含手机与平板、本地与 SMB 对照、英/日/中文对白、音乐下对白和短轻声；覆盖开启、seek、1x/2x、前后台和连续播放。记录冷启动总时长、PCM/ASR/MT/提交各阶段、首条可见字幕时间、连续领先秒数、错过显示的对白比例与人工校对错误率。已有诊断只保存最近窗口，且不包含初始模型准备，不能直接据此宣称端到端首句达标。只保留非敏感汇总指标，不记录字幕、音频、路径或凭证。
